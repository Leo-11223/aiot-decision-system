# AIoT 智慧感測數據應用——預測維護與異常診斷

> 大數據告訴我們過去發生什麼；AI 預測未來可能發生什麼；決策引擎則決定現在應該採取什麼行動。

本專案依照企業命題「IoT 大數據 × AI 決策」的 5 段閉環，把 7 個場域的實際感測資料串成一套**可執行、可解釋、可驗證**的決策系統。

## 一、命題對照表

| 命題要求 | 本專案實作 | 程式位置 |
|---|---|---|
| **01 IoT 感測**：水質、設備、環境的現場即時事實 | 7 個場域、70+ 個感測點位（羊舍環控、水產池水質＋馬達、河川水質、3 座空品站、工地微氣候） | `data/*.csv` |
| **02 大數據**：清洗、儲存、關聯，建立歷史基準 | UTF-16 解碼、時間補齊、**感測器可信度 0–100**（缺值／斷線／超出物理範圍／突波／卡值／三探棒表決／鄰站比對／THI 重算比對）、每小時時段的中位數＋MAD 基準 | `aiot/data.py` |
| **03 AI 分析**：異常偵測、預測、診斷可能原因 | ① 狀態辨識：THI、WQI、AQI、PM10 分級 ② 異常偵測：每小時時段基準 robust z ＋ IsolationForest ③ 趨勢預測：1–6 小時直接多步梯度提升，與持續法比較，**沒贏就不採用** ④ 設備故障機率：馬達 24h 停機分類模型 ⑤ 異常診斷：原因＋證據＋可信度 ⑥ **每週擴展視窗重訓＋預測準度追蹤**（見下方「自我學習」） | `aiot/analysis.py`、`aiot/decision.py` |
| **04 決策引擎**：結合規則與風險，選擇最佳行動 | 目標／規則／風險／成本 → **標準決策資料**（設備／動作／時間／幅度／理由／預期效果／風險／人工確認／Fallback） | `aiot/decision.py` |
| **05 執行回饋**：SCADA／PLC 執行，驗證結果再學習 | **執行**：核准的設備動作轉成 Modbus TCP 控制指令（功能碼 05／06、站號、位址、值），送往**模擬控制器**，約 2 秒後回報「設備已執行」並回讀數值；通訊中斷時「下發失敗 → 自動改派人工 → 人員回報完成」；自動執行的決策由系統直接下發，設備狀態沒變不重複下發。**回饋**：由現場實際動作紀錄計算「動作 → 環境變化」（與同時段未動作配對比較），寫入成效資料庫 `effect_db.json`；決策引擎依「當下時間」以前的紀錄重算成效，樣本達驗證門檻後動作自動由人工確認升級為自動執行、風扇台數由保守全開改為依成效推算；羊舍逐小時**閉環回放** | `backend/control.py`、`aiot/feedback.py` |
| **AI 決策回答三個問題** | 現在發生什麼／接下來會怎樣／現在該做什麼 → 儀表板 ①②③ 區 | 儀表板 |
| **AI 決策輸出**：狀態辨識、異常診斷、趨勢預測、行動控制、管理優先 | 狀態表、診斷表、預測表、決策清單、工單（嚴重度 × 類別權重，含備品與期限） | `outputs/` |
| **安全控制原則** | 低風險＋已驗證＋可信度 ≥80 → 自動執行；中高風險或未驗證 → 人工確認；可信度 <50 → Fallback | `decision.gate()` |

## 三、執行方式

```bash
pip install pandas numpy scikit-learn
python run.py          # 跑完整閉環，輸出 outputs/decisions.json、decisions.csv、work_orders.csv、effect_db.json
python export_dash.py  # 產生儀表板資料表 outputs/dash/*.csv
```

調整門檻、設備、合理範圍：只改 `aiot/config.py`，不必改程式。

### 後端 API（FastAPI）

```bash
py -m pip install -r requirements.txt
py -m uvicorn backend.main:app --reload
```

啟動約 1 分鐘（載入資料並訓練模型），看到「API 已就緒」後，用瀏覽器開 http://127.0.0.1:8000/docs 即可逐一測試。

| 方法 | 路徑 | 用途 |
|---|---|---|
| GET | `/api/sites` | 7 個場域狀態總覽 |
| GET | `/api/sites/{site_id}` | 單一場域完整快照：狀態、診斷、預測、決策、工單 |
| GET | `/api/sites/{site_id}/series` | 時間序列（畫曲線用），含每點感測可信度 |
| GET | `/api/decisions` | 所有標準決策，可用 `mode` 篩選「人工確認」 |
| POST | `/api/decisions/{id}/review` | 人工核准（approve）或駁回（reject） |
| GET | `/api/reviews` | 審核紀錄 |
| GET | `/api/work-orders` | 工單（依優先分數排序） |
| PATCH | `/api/work-orders/{id}` | 更新工單狀態：待派工／處理中／已完成 |
| GET | `/api/feedback` | 動作成效驗證結果 |

| GET | `/api/control/commands` | 控制指令紀錄與模擬控制器回報 |
| POST | `/api/control/commands/{id}/manual-done` | 下發失敗改派人工後，回報現場已完成 |
| POST | `/api/control/sim` | 模擬通訊中斷（測試失敗流程） |

另有 `GET /api/sites/{site_id}/timeline`（整段期間每小時等級與事件標記，時間拉條用），`series` 可加 `step` 參數把資料彙整成每 N 小時的平均、最小、最大值。

### 前端介面（React + TypeScript + Vite）

先啟動後端，再開第二個終端機：

```bash
cd frontend
npm install
npm run dev
```

瀏覽器開 http://localhost:5173 。場域頁最上方用三句白話回答命題的三個問題（現在發生什麼／接下來會怎樣／現在該做什麼，`aiot/explain.py` 只用快照裡已有的資料組句），每張決策卡片也有一句話說明。按「播放」即進入**即時模式**：時間一小時一小時往前走，等級變化、新診斷、新的待核准決策、系統自動下發都會在右上角通知，有新決策待核准時可自動暫停。總覽列出 7 個場域；點進場域頁，可用時間拉條（可調刻度、顯示範圍、播放速度）回放任一時間點，核准或駁回決策、更新工單狀態。網址會記住時間點，例如 `#/site/sheep?at=2026-07-20T14:00`，可以直接分享給隊友。

### 執行回饋（閉環）

`GET /api/feedback/outcomes` 依「當下時間」評估每筆核准：目標是否在期限內達成，並比對設備紀錄確認現場是否真的有執行；現場未執行的核准不計入成效樣本。`GET /api/feedback/rules` 統計每條規則的核准／駁回與成效驗證進度：動作需累積 30 個樣本且單尾 95% 顯著（效果 + 1.645 × 標準誤 < 0）才升級為自動執行；被審核 3 次以上且駁回率 ≥ 50% 的規則標為「建議檢討」。門檻在 `aiot/config.py` 調整。前端對應場域頁的「執行回饋」面板與 `#/feedback` 頁。

所有查詢都可以加 `at` 指定「當下時間」（例如 `at=2026-07-20T14:00`），系統只使用該時間點以前的資料、只用該時間點以前最後一次重訓的模型，回放時不會偷看未來（以「資料截斷到 T 後重建整套系統，T 的結果必須完全相同」的測試驗證，7 個場域皆通過）。場域 id：`sheep`、`expert`、`river`、`breed1`、`breed1_north`、`northeast`、`site`。審核與工單狀態存在 `outputs/aiot.db`（SQLite）。

### 自我學習：每週重訓與預測準度追蹤

預測模型、馬達停機模型、異常偵測的基準，每 7 天用「到那天為止」的全部資料重新訓練一次（`aiot/analysis.py` 的 `RETRAIN_DAYS`）：前 70% 訓練、後 30% 驗證，沒勝過持續法（未來＝現在）就不採用。新資料進來後重複同一流程，資料越多模型越完整。

- **回放不偷看未來**：時間點 t 只使用 t 以前最後一次重訓的模型；第一次重訓前資料不足，先用持續法並在畫面標示。停機模型的答案是「未來 24 小時有沒有停機」，所以訓練時排除最後 24 小時答案還不完整的資料。突波判斷改用過去 30 天的變化分布，短缺值改用前一筆延續（不用前後內插），都是為了不用到未來的讀值。
- **預測準度追蹤**：場域頁「預測準度」區塊比較「重訓時驗證誤差」、「近 7 天實際誤差」（當時做的預測 vs 後來的真實值）與持續法。近期誤差比驗證時大 1.5 倍以上標「誤差變大」（建議提早重訓），輸給持續法標「不如持續法」。
- **模型大小**：使用較小的梯度提升樹（60 輪、每棵 15 葉），實測比原本 200 輪的模型更準、訓練快約 5 倍；全部重訓約 70 秒，存檔 40 MB，雲端記憶體約 250 MB。

自我學習共有四層：預測模型依誤差重訓；動作成效隨樣本累積升級執行模式；常被駁回的規則標示檢討；失效的感測器自動排除。門檻與規則的修改保留給人決定，避免系統學錯造成損失。

## 登入與權限

所有頁面與 API 都要登入。員工可以看資料、核准／駁回決策、更新工單；管理員另外有「管理」頁，可查看操作紀錄（登入、核准、駁回與原因、工單狀態變更、帳號異動、登入失敗）並新增、停用帳號或重設密碼。密碼以 PBKDF2 加鹽雜湊儲存，連續輸錯 5 次鎖 5 分鐘。

第一次啟動會自動建立管理員帳號 `admin`：有設定環境變數 `ADMIN_PASSWORD` 就用它，否則隨機產生，印在後端啟動訊息並存到 `outputs/initial_admin.txt`。其他環境變數見 `backend/auth.py` 開頭說明（`SECRET_KEY`、`ADMIN_USERNAME`、`SEED_USERS`）。

## 部署（Render 免費方案）

`Dockerfile` 把前端網頁與後端 API 包成同一個服務，並在打包時先訓練好模型（`python -m backend.warm` 產生 `outputs/engine.pkl`），雲端主機啟動時只需讀檔（本機實測 1.8 秒，記憶體約 240 MB）。伺服器會先開啟連線埠、在背景載入，載入期間網頁顯示「系統啟動中」。

1. 在 render.com 用 GitHub 帳號登入，New → Web Service，選這個儲存庫（私人儲存庫可以）。
2. Language 選 Docker，Instance Type 選 Free，Advanced 的 Health Check Path 填 `/api/health`。
3. 建立後等它打包（含訓練模型），完成後會得到 `https://<名稱>.onrender.com`。

部署到 Render 時，在 Environment 設定 `SECRET_KEY`（任意長亂碼）、`ADMIN_PASSWORD`，以及 `SEED_USERS`（例如 `amy,初始密碼,staff,王小美;bob,初始密碼,staff,陳大明`）。免費方案重啟會清空資料庫，靠這些變數每次自動建回帳號。

免費方案的限制：15 分鐘沒人使用會休眠，下次開啟約需 1 至 2 分鐘喚醒；檔案系統不保存，重新啟動後審核紀錄會清空；CPU 只有 0.1 核，切換時間點會比本機慢。Demo 前幾分鐘先打開網址喚醒。網址任何人都能開啟，但必須登入才能查看資料與核准決策。

## 四、誠實的限制

- **成效驗證樣本少**：羊舍風扇只有 12 小時的實際開啟紀錄，開啟時 THI 比同時段平常多降 0.53 ± 0.76（前後 2 小時變化量），尚未達統計驗證，因此依安全原則列為「人工確認」。
- **風扇台數無法單憑現有資料推算**：開啟時段中 77% 是 4 台同時開，資料分不出 2 台與 4 台的差別。因此規則（`decision.fan_plan`）分兩種情況：
  - **效果已驗證**（≥30 筆且單尾 95% 顯著）：用成效的保守估計值算出每台效果，依「要降多少 THI」反推台數；全開仍不夠時，自動加派噴霧與飲水。
  - **效果未驗證**（目前）：危險級全開（電費約 NT$12／小時，遠低於熱緊迫損失，也才能累積樣本）；警戒級試驗開 2 台，與全開形成對照，累積不同台數的資料。
  樣本累積到門檻後，系統會自動從「保守全開」切換為「成效推算」，這就是閉環「再學習」。以目前不完整的資料粗估，全開 4 小時約只能多降 1.1，可能不足以把 THI 從 82 降到 79 以下，代表羊舍單靠風扇可能不夠，需要現場確認通風設計。
- **部分預測模型未勝過持續法**：每次重訓都會重新比較，水產池 DO、河川等多數時段模型沒贏，系統自動改用持續法並在畫面標示，不硬用模型。資料前段只有幾天可訓練，模型的表現較差，這是只用當時資料的真實結果。
- **控制器是模擬的**：本專案沒有連到現場設備。羊舍的線圈位址取自資料欄位名稱中的點位編號（例如「南右帆布張 23/24」、「風扇-03」），專家系統馬達與工地灑水的位址為假設值。正式導入時只需把 `backend/control.py` 的 `SimController` 換成企業現有 SCADA／PLC 的通訊模組，指令格式與流程不變。
- **設備狀態碼 2／4** 的意義以資料推斷（所有點位同時出現 → 控制器層級異常），需現場確認。
- 成本採假設值（風扇 0.75 kW、電價 NT$4/kWh），可在 `decision.py` 替換。
- 各場域資料期間不同，「當下」以各場域最後一筆資料計。
